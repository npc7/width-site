## 一句话

**先筛查，再归集。** 问题资金一旦归集进热钱包，就和正常资金混在一起，很难再拆开。别人再筛你的热钱包，也会查到这笔关联。

## 为什么要在归集前

归集在链上就是一笔普通转账：从用户的充值地址转到你的归集地址，签名由 MPC 完成。托管方的「自动归集」，拆开就是三步：找出余额够了的充值地址、补手续费、调用签名接口转走。

这三步都可以自己做。自己做的好处是：**KYT 放在哪一步、用什么规则，由你决定**。把筛查放在归集之前，热钱包里就只有干净的钱。

## 流程

```text
充值到账 ──► DART 筛资金来源 ──► 通过 ──► 进入归集队列 ──► MPC 签名归集
                    │
                    └─► 复核 / 加强尽调 / 拦截 ──► 这个地址暂停归集，交给合规或客户处置
```

### 第一步：记下每笔充值

用托管方的 Webhook，或定时拉取充值记录。每笔记下：链、交易哈希、充值地址、币种、金额。

### 第二步：筛这笔充值

```json
POST https://api.width.live/api/v3/screen/kyt
X-Api-Key: YOUR_KEY

{
  "chain_name": "Tron",
  "tx_id": "充值交易哈希",
  "token": "usdt",
  "screen_direction": "in",
  "inflow_hops": 3,
  "outflow_hops": 0,
  "in_ruleset_id": 0,
  "mode": "async"
}
```

异步模式立刻返回 `job_id`，再用 `GET /api/v3/screen/result/{job_id}` 取结果。`in_ruleset_id` 换成这个客户的规则集。

### 第三步：按判定决定能不能归集

| 判定 | 分数 | 归集 |
|---|---|---|
| 通过 | 0–19 | 入账，进入归集队列 |
| 复核 | 20–49 | 暂缓，人工看命中路径再决定 |
| 加强尽调 | 50–79 | 冻结入账，请用户补充资金来源材料 |
| 拦截 | 80–100 | 不入账、不归集；资金留在原地址或转入单独的隔离地址，等合规结论 |

**一个地址上只要有一笔充值没通过，整个地址先不归集。** 否则没通过的那笔会跟着其他钱一起进热钱包。

```python
for addr in deposit_addresses:
    deposits = pending_deposits(addr)            # 已入账、待归集的充值
    if any(d.verdict != "accept" for d in deposits):
        continue                                 # 有没通过的，整个地址先不动
    if balance(addr) < MIN_SWEEP_AMOUNT:
        continue                                 # 金额太小，先攒着
    ensure_fee(addr)                             # Tron 委托能量 / EVM 补原生币
    tx = custody.transfer(addr, COLLECT_ADDRESS) # MPC 签名
    save_sweep_record(addr, tx, deposits)        # 记下对应的快照编号
```

### 第四步：提现签名前筛目标地址

客户发起提现时，签名之前对目标地址做 KYA（流入 0 或 1 / 流出 1），通过才进入签名。**充值看来源，提现看去向。**

手续费、能量租赁等归集细节，见博客 [MPC 托管用户自建归集与 KYT 接入指南](/zh/blog/mpc-sweep-kyt-guide/)。

## 按客户分开：规则和留档

你服务的企业客户，风险偏好各不相同：支付客户、交易平台、项目方的容忍度不一样。

- **规则集按客户分开**：复制内置规则集，每个客户一份，按客户的口径改规则和阈值；筛查时传这个客户的规则集。
- **结果按客户留档**：在你的系统里，把每次筛查的快照编号和客户、充值记录关联起来。客户问起某笔充值为什么没归集，按编号调出当时的完整证据。
- **把结论交给客户**：把分数、处置、命中的规则和路径展示给客户的合规人员，由他们决定放行还是退回。

## 存量地址和持续监控

- **上线时**：用 CSV 批量导入存量充值地址，一次性重新筛查，再切到实时筛查。
- **之后**：充值地址之后可能收到新的问题资金，对手方也可能上新的名单。筛查时加 `"auto_monitor": true`，把地址按这次的参数加入持续监控；参数之后可以在监控页修改。见 [持续监控](/zh/docs/monitoring/)。

<div class="callout tip"><b class="t">先拿历史数据跑一遍</b>上线前，拿过去一个月的充值跑一遍，看分数分布，再定你的档位阈值。已经在用其他工具的，可以先并行跑一段时间，对比两边的结果。</div>

## 案例（已匿名）

某钱包与托管基础设施服务商统一接入 DART，为旗下企业钱包的每笔充提做筛查，工作日每天 1.7 万到 1.8 万次。下游企业开箱即有 KYA / KYT，不用各自采购和对接。
